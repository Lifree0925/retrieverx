## WP9 · 检索链路 Trace（数据结构与落库）

**要解决的问题**：检索出问题时，"结果不对"是一句没有信息量的话。
需要能回答：**正确的结果是在哪一层丢掉的**——BM25 就没召回？向量没召回？
RRF 融合后掉了？还是被精排挤下去了？

**实现位置**
- `app/core/trace.py` — `TraceStore` 负责落库（Redis，带 TTL）与 `candidates_snapshot()` 快照序列化
- `app/models/retrieval.py::RetrievalTrace` — Trace 的数据模型
- `app/api/routes_trace.py` — `GET /trace/{request_id}` 回查接口

**状态**：已实现。Redis 不可用时**静默降级**（Trace 查不到，但检索照常），
这是刻意的取舍——观测数据不该成为主链路的单点故障。

**怎么验证**：调 `POST /search`，从响应里取 `request_id`，再 `GET /trace/{request_id}`，
应能看到 `bm25_candidates / vector_candidates / rrf_candidates / final_candidates` 四层快照与分阶段耗时。

## WP10.2 · 固定切块基线（刻意保留的"不采用方案"）

**要解决的问题**：怎么证明"结构感知切块"比"固定长度切块"好？
没有基线就没有对比，只能说"我觉得这样更好"。

**实现位置**
- `app/core/chunker.py::FixedChunker` — 把整份文档文本拍平后按固定字符窗口滑切，
  **刻意丢弃** `heading_path`、`content_type` 与精确 `page_number`

**状态**：已实现，且**只作为消融基线存在**，不代表推荐做法。
类里写清了"它丢掉了什么"，那些被丢掉的东西就是"结构感知"赚到的部分。

**为什么单独给它一个工作包**：因为它看起来像"没写完的代码"。
没有编号与说明，下一个人很可能把它当成死代码删掉，顺手把基线也删了。

## WP10.5 · 切块消融实验

**要解决的问题**：把固定切块与结构感知切块放在**同一份评测集**上跑，用 Recall/MRR/NDCG 说话。

**实现位置**
- `scripts/run_chunking_ablation.py` — 同一份 PDF，两套切块，对比结构保留质量与指标

**状态**：脚本已实现。**注意命题的完整范围**：脚本目前回答的是"结构保留质量"
（标题路径、表格是否完整、块大小分布）；要回答完整命题"Recall 是否真的改善"，
需要一份人工核对的评测集 —— 用 `scripts/build_eval_set.py` 生成后再接进来。

## WP14 · 失败分类学（Failure Taxonomy）

**要解决的问题**：`Recall@5 = 0.6` 只说"有 40% 没召回"，不说**为什么**。
需要一套可归因的分类，让"改进"有明确靶点。

**实现位置**
- `app/evaluation/failure_analysis.py` — 失败类型定义与归类逻辑
- `scripts/run_failure_analysis.py` — 跑一遍评测集并输出各类失败的数量分布

**分类的核心维度**：按**丢失的层级**归因——
在 BM25 层就丢了 / 向量层丢了 / 融合后丢了 / 被精排挤下去了。
前三种靠 wp9 的四层快照区分，第四种需要比较 `rrf_candidates` 与 `final_candidates`。

**状态**：已实现，并在实现过程中发现自己原先的一个漏洞：
早期版本把"执行成功 + 审计通过"一律算成功，
于是"结果错但没报错"这类失败被整类漏掉（新增 `AUDITOR_FALSE_NEGATIVE` 类型 + 单测）。

**诚实标注**：这是**启发式归类**，不是权威判定。报告里必须写清"启发式"，
否则会被人当成精确度量来引用。

**已知边界**：`RERANK_ERROR` 的判定依赖 `final_candidates` 快照，
而快照只保留前 10 条（`trace.py`），所以 `top_k > 10` 时会误判。

## WP15 · 反馈闭环与策略自适应

**要解决的问题**：让用户反馈真正作用于检索，但**不能"一点差评就改权重"**。

**实现位置**
- `app/core/feedback.py` — `FeedbackStore`：反馈落 Redis、按查询取回、更正缓存
- `app/core/retrieval_policy.py` — `RetrievalPolicy`：按查询类型维护 BM25/向量权重 + 版本号 + 回滚
- `scripts/run_feedback_experiment.py` — 反馈前后对比实验

**三重约束**（这是本工作包的核心，也是面试重点）
1. **最小样本量** `POLICY_MIN_SAMPLES`：样本不足直接拒绝更新；
2. **单次最大步长** `POLICY_MAX_STEP`：每次只小幅调整，防剧烈抖动；
3. **版本号 + 历史**：`history` 记录每次变更，`rollback()` 可回滚。

**状态**：机制已实现且默认权重来自 `.env`（`BM25_WEIGHT` / `VECTOR_WEIGHT` 是基准比例）。
但 **API 从不主动调用 `update()`** —— 自适应目前只在离线实验脚本里生效，
线上重启即回到默认策略。这是刻意的 MVP 取舍，不是遗漏。

## WP18 · Retrieval Debugger（把 Trace 摊开给人看）

**要解决的问题**：WP9 把链路数据存下来了，但只有调接口才能看到。
调试时更需要"提问完直接在界面上看到 BM25/向量/RRF/精排各阶段的 Top-N 与耗时分解"。

**实现位置**
- `streamlit_app.py` — 检索标签页里的「链路 Trace」折叠区

**状态**：已实现。

**为什么和 WP9 分开编号**：WP9 是**数据结构与落库**（后端契约），
WP18 是**展示层**（前端体验）。两者可以独立演进——
比如换掉 Streamlit 也不会影响 Trace 的数据结构。
